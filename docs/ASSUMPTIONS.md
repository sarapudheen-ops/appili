# ASSUMPTIONS.md — Open Assumptions & Interpretations

Per [AGENTS.md](../AGENTS.md): *"If an assumption is needed, stop and document it here. Do not
guess."* This file records interpretations made while authoring governance documents. None of
these authorize a vehicle-specific byte value; those remain `UNKNOWN - PENDING_PHYSICAL_LOG`.

| # | Assumption | Why it was needed | Impact if wrong | Status |
|---|---|---|---|---|

- No OBD-II protocol (ISO 9141-2, ISO 14230-4/KWP, ISO 15765-4/CAN, J1850) has been selected,
  suggested, or ranked for this vehicle.
- No ECU address, header (`ATSH`), init sequence, baud rate, or timing parameter has been chosen.
- No PID, DID, or routine identifier has been defined.
- No build tooling, module layout, or Gradle/Kotlin source has been created in this phase.

## Phase 3 — Bluetooth Classic RFCOMM transport

| # | Assumption / decision | Why it was needed | Impact if wrong | Status |
|---|---|---|---|---|
| A11 | `BLUETOOTH_SCAN` is declared in the manifest and modelled in the permission provider, but **nothing depends on it**: this phase performs no discovery, so the transport gates only on `BLUETOOTH_CONNECT`. | The brief names both permissions; discovery is out of scope, and gating connection on `SCAN` would break a user who granted only "Nearby devices: connect". | If a later phase adds discovery, `SCAN` must become a hard gate at that point. | Open — deliberate |
| A12 | The transport resolves the selection by **MAC address** (`adapter.getRemoteDevice(address)`), and selection is set only from a UI tap. | The brief forbids choosing an adapter by name; an address is the only stable identity the platform gives us. | None expected. Address is display-only data. | Settled |
| A13 | `io.mockk:mockk` is added as a **test-only** dependency. | `BluetoothSocket`, `BluetoothDevice`, and `BluetoothAdapter` are final classes; MockK's inline instrumentation is the supported way to mock them on the JVM. | Alternative is Robolectric or a hand-rolled socket seam; both are heavier or less faithful. | Provisional |
| A14 | The permission provider is **snapshot-based** (`state()` + explicit `refresh()`), refreshed on activity resume and after the permission dialog returns. | A live permission listener does not exist on Android; polling or lifecycle-driven refresh is the available mechanism. | A revocation while the app is foregrounded is noticed at the next refresh, not instantly. Connect re-reads the state and fails closed regardless. | Open |
| A15 | `connect()` holds the transport mutex while the RFCOMM handshake runs, so `disconnect()` during `CONNECTING` waits for the attempt to finish or fail. | A blocking `socket.connect()` cannot be cancelled by coroutine cancellation; closing the socket mid-handshake is what actually aborts it. | A slow/hung handshake delays a user-initiated cancel. Worth revisiting with a timed connect + socket close on cancel. | Open — known limitation |
| A16 | A locally initiated `disconnect()` always lands in `DISCONNECTED`, never `ERROR`, even though closing the socket makes the pending `read()` throw. | Reporting a user's own action as a fault trains users to ignore error states. Link-generation guarding makes the stale read loop unable to publish `ERROR` over a newer state. | None — covered by a dedicated test. | Settled |

## Phase 4 — ELM adapter engine

| # | Assumption / decision | Why it was needed | Impact if wrong | Status |
|---|---|---|---|---|
| A17 | `ElmChannel` subscribes to `incomingBytes()` **per command** (inside the timeout window) rather than running one long-lived collector. | The transport contract guarantees only a single consumable stream; per-command subscription keeps the channel free of a background scope it would have to own and cancel. Bytes arriving between commands stay buffered in the transport. | If an adapter emits unsolicited chatter while idle, it becomes the prefix of the next response. Acceptable while only known AT commands run; must be revisited before OBD polling. | Open — known limitation |
| A18 | A response is returned as **one whitespace-free string**, with multi-line replies concatenated (`"41 00 BE 3F\r…"` → `"4100BE3F"`). | The brief specifies exactly this normalization, and it is all the initializer needs. | Multi-line PID/frame responses will need line-level access later; that belongs in the OBD layer, not here. | Open — deliberate |
| A19 | Added `ElmException.LinkClosed` beyond the brief's token list. | If the stream completes without a prompt, `Flow.first {}` throws `NoSuchElementException`; letting that escape would be an untyped crash and would blur "link died" with "adapter stayed silent". | None — additive; `Timeout` keeps its exact meaning. | Settled |
| A20 | Command strings are validated: blank or line-terminator-containing commands are rejected before any byte is written. | `"ATZ\rATE0"` would inject a second command and desynchronise the request/response pairing. | None — a caller building commands from user input is refused early. | Settled |
| A21 | `ATSP0` is sent as part of initialization even though the vehicle protocol is unverified. | The brief requires it, and it selects *automatic* detection: it pins nothing and presumes no protocol. Nothing downstream may issue a vehicle request until the matrix is verified. | If the pilot vehicle's protocol is later verified, auto-detect can stay or be replaced by an explicit `ATSP<n>` — a matrix-driven decision, not a default. | Open |

## Phase 5 — Read-only OBD-II decode (modes 01/03/07/09)

| # | Assumption / decision | Why it was needed | Impact if wrong | Status |
|---|---|---|---|---|
| A22 | Decoder fixtures are **authored from the SAE J1979 formulas**, not captured from a vehicle: `41 0C 1A 20` → 1672 rpm, `43 02 01 33 00 00` → `P0133`, `49 02 01 …` → a VIN. | There is no adapter and no vehicle in the authoring environment, and the brief requires decoder tests to run against J1979 vectors. | The tests prove the arithmetic matches the published formula and that absence is not numeric zero. They do **not** prove how this vehicle answers; every protocol/ECU field stays `UNKNOWN - PENDING_PHYSICAL_LOG` (A7). | Open — replace with captures when `docs/captures/` exists |
| A23 | For modes 03/07 the payload's **parity** decides the framing: an even number of bytes after the service byte is all whole DTC blocks (ISO 9141-2 / 14230), an odd number means the leading byte is a DTC count (ISO 15765). An announced count larger than the blocks present is `Malformed`. | CAN prefixes a DTC count and the K-line protocols do not, while the protocol is still unverified (A21). The alternative — inferring framing from `ATDPN` — would add a request and a second way to be wrong. | A payload that is oddly shaped for another reason is rejected as `Malformed` instead of being silently misaligned into wrong codes. | Open |
| A24 | `0x0000` DTC blocks are **discarded**, never reported as `P0000`. | Adapters pad DTC payloads to a full frame with zero blocks. | A vehicle that genuinely stored `P0000` (not a real fault code) would be reported as having no code. | Settled |
| A25 | A VIN is located by scanning for the **printable run** rather than trusting a fixed byte offset, then validated (17 characters, no `I`/`O`/`Q`); trailing frame padding is ignored. | Multi-frame mode 09 answers differ in whether the "number of data items" byte is present and how frames are padded. | A payload whose first 17 printable characters are not a valid VIN becomes `Malformed`, never a truncated or subtly wrong VIN. | Open |
| A26 | Only negative response code `0x12` becomes `Unsupported`; every other `7F <service> <nrc>` becomes `Malformed`. | The result type separates "this vehicle does not support it" from "this answer is unusable"; interpreting further codes (busy, conditions-not-correct, security) needs policy that does not exist yet. | A vehicle answering e.g. `0x22` (conditions not correct, engine off) shows `Malformed` rather than a more specific reason. | Open — revisit once captures exist |
| A27 | The request seam is a **domain-owned port**: `ObdCommandPort` lives in `domain.obd`; `ElmObdCommandPort` in `adapter.elm` maps `ElmException` onto `DiagnosticResult`. `domain` imports no adapter or Android type. | The standing rule is that decoders stay pure Kotlin, yet *something* has to translate `ElmException.Timeout` into `DiagnosticResult.Timeout`. Putting the port in the domain keeps the dependency pointing adapter → domain (the direction `AGENTS.md` describes) with no cycle. | Moving the port to the adapter would make the engine untestable without the adapter package and reintroduce the coupling the rule forbids. | Settled |
| A28 | Every request uses the channel's **2000 ms** default budget; the engine does not extend it for multi-frame VIN reads and does not retry. | No physical log exists to justify a per-request timeout, and an invented one would hide slow-link behaviour. | A slow link reports `Timeout` — honest, and distinguishable from `NoResponse` — instead of a partial VIN. The budget can be tuned per request once measured. | Open |
| A29 | Supported-PID banks are **not walked automatically**: `ObdService.supportedPids(base)` answers for one bank and the caller decides whether to follow `SupportedPids.continuesToNextBank`. | Walking all four banks multiplies requests and timeout exposure, and nothing yet consumes the union. | A caller that ignores the continuation bit under-reports support; it cannot over-report it. | Open — deliberate |
| A30 | **Mode 04 (clear DTCs) and modes 21/22 are absent, not disabled.** There is no method and no command builder that can produce them. | `AGENTS.md` Rule 2 and `docs/PRODUCT_SCOPE.md` §2.2 forbid physical writes; "read-only" is only credible if it is unreachable rather than unexercised. | A future read-only clearing feature would require amending PRODUCT_SCOPE first — intentionally. | Settled |

## Phase 6 — Compose scan & live-data UI

The phase-6 brief asks for a scan screen, a live-data screen and a session export, which means the app
finally *does* ask the vehicle questions. A21 and the "no diagnostic operation" line in the README are
therefore superseded **for generic reads only**, and only after an explicit tap from the user.

| # | Assumption / decision | Why it was needed | Impact if wrong | Status |
|---|---|---|---|---|
| A31 | The UI issues only **generic** mode 01/03/07/09 requests (`0100`, `0120`, `0140`, `010C`, `010D`, `0105`, `03`, `07`, `0902`) plus `ATI`/`ATDP`, and only from an explicit user action (Scan, or Start live data). Everything in `docs/VEHICLE_MATRIX.md` stays `UNKNOWN - PENDING_PHYSICAL_LOG`; no manufacturer-specific (mode 21/22) or clear (mode 04) request exists. | The brief requires the scan screen to show supported PIDs, stored/pending DTCs and the VIN, which cannot be done without these reads. | Overstating the app's knowledge would be the failure mode; nothing here claims a per-vehicle result. | Open — supersedes A21 for generic reads |
| A32 | The connection screen shows identity and protocol **as the adapter reports them** (`ATI` → `ELM327 v1.5`, `ATDP` → `AUTO, ISO 15765-4 (CAN 11/500)`) and labels them as adapter claims, not as verified vehicle facts. | `ATI`/`ATDP` are the only sources available without the physical log, and both can be wrong (clones report false firmware, `ATDP` reports the *negotiated* protocol). | A Vgate-labelled dongle reporting `ELM327 v1.5` is normal; the UI must not present it as a firmware guarantee. | Open |
| A33 | Supported-PID discovery walks banks **only while the continuation bit is set**, stops at the first unanswered bank, and requests at most the four banks the decoder supports (`00/20/40/60`). | A29 left bank walking to the caller; the scan screen is that caller. Stopping at the first failure keeps one bad bank from multiplying into four timeouts. | A vehicle whose `0120` times out once is reported as having only bank `00` known — under-reporting support, never over-reporting. | Open — deliberate |
| A34 | A PID the bitmask **excludes** is never requested, and is displayed as "Not Supported" rather than being polled and shown as `No Response`. | Distinguishing "the ECU says it has no such PID" from "the ECU said nothing" is the whole point of honest modelling; requesting it would also invent traffic the vehicle cannot answer. | None; the demo PID `0x05` (coolant) is exactly this case, and a test asserts no `0105` write happens. | Settled |
| A35 | When **no** supported-PID bank answers, support is `null` (unknown), not `false`, and the known PIDs are still polled. | Treating "we could not read the mask" as "the vehicle supports nothing" would blank the screen and look like a healthy but silent car. | An unreadable mask yields "Not Supported" nowhere and live values everywhere the ECU answers — honest either way. | Settled |
| A36 | Live data polls **sequentially** (no concurrent requests), 600 ms between cycles, reads the supported-PID mask **once per polling run** rather than per tick, and **stops when the host leaves the screen** (`ON_STOP` → `onHostStopped`). | One command may be in flight (phase-4 rule); re-reading the mask every 600 ms would triple traffic for a value that does not change; and polling unseen keeps the radio and the bus busy for numbers nobody is looking at. | A PID that the ECU starts reporting mid-drive stays "Not Supported" until polling is restarted. | Open — deliberate |
| A37 | Export is a **share-sheet text payload** (`ACTION_SEND`, `text/plain`), not a file: no `FileProvider`, no storage permission, no file left behind. The log is session-scoped and survives disconnect so the user can still share it. | The brief asks for a button that exports; writing to external storage would need permissions and would leave a sanitised-but-still-vehicle-identifying artefact on disk unmanaged. | On a device without a share target the button reports that nothing could receive the text. | Open |
| A38 | "Sanitized" means the **VIN (both as text and as its hex form) is replaced by `SessionSanitizer.VIN_PLACEHOLDER`**, and adapter MAC addresses are removed. DTCs, PIDs, values, commands and timestamps are **kept verbatim**. | A session log is worthless as evidence if the numbers are masked, but a VIN is a vehicle identifier that should not travel in a bug report by default. | Removing the placeholder later is a one-line change in `SessionSanitizer`; adding fields is additive to schema `appili.session.v1`. | Settled |
| A39 | The CSV export is **one rectangular table**: each row repeats `sessionStartedAt,adapterIdentity,protocol,readOnly,sanitized` before the per-entry columns. | A two-block CSV with a session header above a log header breaks every spreadsheet/`csv` parser. | None — a parser reads it as a normal table. | Settled |
| A40 | The scripted adapter (`DemoByteTransport`, `DebugAppiliApp`) lives in the **`debug` source set**, so release builds contain neither the demo transport nor the AT console; the AT console is additionally gated on `BuildConfig.DEBUG` in the view model **and** in `ConnectionScreen`. | The standing rule is that no arbitrary command field may ship in a release build, and a scripted "vehicle" must never be reachable in production where its invented replies could be mistaken for a car. | A release APK shows a disabled demo button and no console. | Settled |
| A41 | The demo transcript is **authored**, not captured, and is labelled as such in the code and on screen ("demo adapter — responses are scripted"). | Same reason as A22: there is no adapter in the authoring environment, and a fabricated transcript presented as a capture would be indistinguishable from real evidence later. | The screenshots/flow this enables demonstrate *plumbing and presentation*, not vehicle behaviour. | Open |
| A42 | No Android emulator and no JDK were available, so **the phase-6 gate (`lintDebug testDebugUnitTest assembleDebug`) and the requested emulator run are UNRUN**. | See A9. AGENTS.md requires the gate before merge; claiming a pass, or claiming screenshots were taken, is exactly what this repository forbids. | Treat the gate and the screenshots as outstanding tasks; the substitute check is recorded in the README. | **BLOCKING — must be run before merge** |

## Phase 7 — Vehicle profiles (JSON) and the fail-closed matching gate

| # | Assumption / decision | Why it was needed | Impact if wrong | Status |
|---|---|---|---|---|
| A43 | Profiles are **pure JSON files in `app/src/main/assets/profiles/`**, read by a hand-written strict JSON reader in `domain.profile`. No `org.json` (Android-only; its JVM stubs throw), no serialization library (would need a Maven repository the authoring environment cannot reach — A9). The reader is dependency-free and has no reflection. | The domain layer must stay pure Kotlin with zero Android imports, and the phase had to be writable in this environment at all. | A library would give streaming and better diagnostics; the schema is small and static, so the cost is only code volume (~200 lines, fully tested). | Open |
| A44 | Parsing is **whitelist-strict**: unknown keys are an error, duplicate keys are an error, the root `status` must equal the status derived from the ECUs, and `UNKNOWN` is accepted only where the schema allows it (`txId`, `rxId`, `network`, `initCommands`). | A misspelt field (`"staus": "VERIFIED"`) must not produce an accepted-but-wrong profile, and a file may not claim more verification than its ECUs have. Silently ignoring input is the failure mode that makes safety files dangerous. | Adding a field to the schema requires touching the parser's key sets — deliberately, so the schema stays a contract. | Settled |
| A45 | The brief puts `status` on `EcuDefinition`, so that is where it is modelled; `VehicleProfile.status` is **derived** as the weakest claim among its ECUs, and the gate checks both the derived profile status and the target ECU's own status. | "An operation can only run if its profile status is VERIFIED" needs a profile-level answer, but the schema has no profile-level field. Weakest-wins is the only reading that cannot be gamed by adding a second, unverified ECU. | If a future schema adds a real profile-level status, the derived property becomes a consistency check rather than the source of truth. | Open |
| A46 | A [DiagnosticOperation] **cannot be constructed** with a service outside the J1979 generic read set (01, 02, 03, 05–0A). `04` (clear), `2E`/`2F` (write), `31` (routine), `21`/`22` (manufacturer) and the rest are rejected by `require` in the constructor. | "No write operations are permitted in profiles yet" is only credible if a profile *cannot describe* one — the same absent-not-disabled doctrine as A30. | Adding a service later means amending this allowlist first, on purpose. | Settled |
| A47 | The gate refuses `ACTIVE_TEST` and `CONFIGURATION` operations **even on a `VERIFIED` profile** (`RISK_CLASS_FORBIDDEN`). | AGENTS.md Rule 2 wires actuator tests and configuration changes to the simulator only; a verified read profile does not change that. | When a simulator execution path exists, it needs its own branch — it must not be a loosened check here. | Open — deliberate |
| A48 | An operation is also refused unless its **service byte is declared** in the target ECU's `supportedServices` (`SERVICE_NOT_DECLARED`). The candidate profile declares `[]`. | An operation existing in a profile says nothing about the ECU answering it; declaring the service is the capture that makes it real. It also means the candidate profile denies reads even if someone flipped its status to `VERIFIED` without a dump. | A vehicle whose services are captured but not listed denies everything until the list is filled in — under-permissive, never over-permissive. | Open — deliberate |
| A49 | `app/src/main/assets/profiles/toyota_innova_2007_gcc.json` carries `"status": "UNVERIFIED"`, `UNKNOWN` for `txId`/`rxId`/`network`/`initCommands`, an empty `supportedServices`, and the note **"Awaiting physical bus dump from authorized tool."** Its four operations are the generic J1979 reads only (`0100`, `010C`, `03`, `0902`). | The brief's candidate profile, and the honest state of `docs/VEHICLE_MATRIX.md`: nothing about this vehicle's bus has been captured. | Nothing may be transmitted from it. That is the point, and a test asserts it for every declared operation. | Open — awaiting the dump |
| A50 | **No UI, view-model or Bluetooth path loads profiles in this phase.** The parser and `ProfileOperationExecutor` have no production caller yet; the phase-6 generic scan remains the only live read path, and the profile gate cannot weaken it because it is not wired. | "Implement ONLY the explicitly requested phase." Wiring profiles into the app would change what the running app transmits, which this phase did not ask for and the gate could not verify by execution (A9). | Profiles are inert until a later phase loads them. Stated plainly rather than implied. | Open — deliberate |
| A51 | The asset test reads the JSON from the module directory (`src/main/assets/profiles/…`, with an `app/…` fallback) rather than through `AssetManager`. | `AssetManager` is Android; unit tests are plain JVM. Reading the real file is what makes the test prove *the shipped asset* and not a copy of it. | If Gradle's test working directory changes, the fallback path list needs another entry; the failure message prints the paths it tried. | Open |
